# i18n — ES/EN prose localization

`aurum/core/i18n.py` is the single source of truth for every user-facing string that is not a number,
a citation, a rule id, or an API response shape. It holds one dictionary (`_STRINGS`) keyed by dotted
key → `{"es": ..., "en": ...}`, and one lookup function, `t(key, lang=None, **kwargs)`.

The `insights.*` keys live in `aurum/core/i18n.py` too; `aurum/insights/i18n.py` is a thin re-export
(`from ..core.i18n import t`) so `aurum/insights/digest.py`/`engine.py`/`telegram.py` import
`from .i18n import t`.

The web UI's own dictionaries (ES/EN screen copy) are a separate, client-side layer described in
[web-ui.md](web-ui.md#i18n) and [design-system.md](design-system.md).

## What is localized, and what is not

Localized (must go through `t(...)`):

- `Explain.summary` — the one-line human summary attached to every numeric result.
- `Step.label` (and `Step.formula` where it is prose, not a citation) — `Explain.add_step(label, value,
  formula=...)`.
- `flags[]` — the plain-language sentences in cross-border/other assessment responses.
- Report `Section.title` / `Section.notes` (`aurum/reports/packs.py`) — the whole point of a report pack
  is a document the reader takes to a preparer, so the section headings and callouts speak one language.
- Insight `title` / `body` (`aurum/insights/engine.py`).

Never localized (stays as-is regardless of `lang`):

- Numbers, `Amount.amount`, `Amount.currency`.
- `Citation.law` / `.article` / `.url` / `.excerpt` — legal citation text is quoted verbatim; translating
  it would misrepresent the source.
- `rule_versions`, rule/insight/pack **ids** (`"us.fed.se_tax@2026.1"`, `"pue_not_collected"`) — machine
  keys the frontend and other services match on.
- `unverified_constants` keys — the web UI renders these as `(verify)` chips directly from the key; do
  not invent a translated label for them (see [web-ui.md](web-ui.md)).
- A `results.*` field that a caller matches on programmatically (e.g. `results["cheaper"] == "buy"` in
  `aurum/plan/scenarios/*.py`) stays an untranslated machine value; only the *displayed* copy
  (`Explain.summary`, a KPI computed from it) is translated. When a function needs both, compute the
  machine key first and pass its translated label into `t(...)` as a format argument — never overwrite
  the machine key with the translated string.
- KPI `label` text in report packs (`aurum/reports/builder.py::KPI`) is intentionally bilingual inline
  (`"Ingreso / Income"`) — report KPIs are meant to be read by someone who may not share the
  workspace's language (an accountant, a co-signer). This is a deliberate exception, not a gap.
- Scenario JSON-schema field labels in `aurum/plan/scenarios/*.py::Inputs` (pydantic field
  names/descriptions) — the schema is the API's contract with the web UI form generator, which
  renders the field labels as the schema gives them.

## `(verify)` markers

Every unverified constant's `mark` (`K.verify_mark(...)`, from `aurum/rules/*/constants_2026.py`) is a
short, language-tagged suffix appended to a step/summary, not a `t()` key of its own — the constant
modules that own it decide the exact text. The convention for every key here: the English word is
**`(verify)`**, the Spanish word is **`(verificar)`**. The web UI's
`(verify)` chips are driven by the `unverified_constants` key list (untranslated, see above), not by
this suffix, so changing the suffix text never breaks the chip.

## Usage

```python
from aurum.core.i18n import t

summary = t("pf.net_worth", lang)                 # static string
summary = t("pf.budget_status", lang, name=label)  # str.format() placeholders
```

`lang` is resolved once per request, as close to the router as possible, and threaded down as an
explicit `lang: str = "es"` (or `str | None = None`, resolved with `ws_lang`) parameter — never read
from a global or re-derived deep inside a rule. The two helpers:

- `resolve_lang(explicit, workspace_language)` — `?lang=` wins when given, else the workspace's
  language, else `"es"`.
- `ws_lang(ws_id, explicit=None)` — same, but looks the workspace up for you; falls back to `"es"` on an
  unknown workspace rather than raising, since callers only use it to pick summary text.

Router convention (used by `aurum/rules/us`, `aurum/rules/crossborder`, `aurum/taxus`,
`aurum/crossborder`, `aurum/holdings`, `aurum/creditreport`, `aurum/plan`, `aurum/business`,
`aurum/reports`):

```python
@router.get("/{ws}/...")
def endpoint(ws: str, lang: str | None = None) -> dict:
    return service.compute(ws, ..., lang=ws_lang(ws, lang))
```

A rule's `compute(...)` method takes `lang: str = "es"` as an explicit keyword (not swallowed by
`**_: Any`) so a caller that does not pass it still gets a valid — Spanish-default — summary; the
registry's `Rule.compute(self, **inputs)` protocol already accepts arbitrary kwargs, so adding `lang`
to a rule never breaks a caller that does not know about it yet.

## Adding a language

1. Add the new language code to `Lang` (`Literal["es", "en", ...]`) in `aurum/core/i18n.py`.
2. Add the third key to every entry in `_STRINGS` you want translated. `t()` falls back to `es`, then
   the raw key, so a partially-translated rollout never raises or shows an empty string — untranslated
   entries just show Spanish until someone fills them in.
3. Update `resolve_lang`/`ws_lang`'s prefix check (`"en" if value.lower().startswith("en") else ...`)
   to a real language-tag parser once there are more than two languages; the two-way ternary is
   intentionally simple while ES/EN is the only pair.
4. Extend `Workspace.language`'s `Literal["es", "en"]` (`aurum/core/workspaces.py`).

## Adding a key

Pick a dotted namespace that mirrors the owning module (`rules.us.fed.<rule>.<field>`,
`business.kpis.<field>`, `plan.<scenario>.<field>`, `reports.<pack>.<section>`, `insights.<kind>`) so a
key's origin is obvious from its name alone. Static text is a plain two-entry dict; text with
placeholders uses `str.format()` syntax (`"{name}: {amount} {currency}"`) — `t()` calls
`template.format(**kwargs)` and silently returns the un-formatted template on a `KeyError`/`IndexError`
rather than raising, so a caller that forgot a kwarg degrades to visible-but-wrong text instead of a
500.

## Coverage

Beyond `pf` and `tax`, `aurum/core/i18n.py` covers, in full for `Explain.summary` and largely for
`Step.label`/`flags[]`/report section title-note/insight text:

- `aurum/rules/us/federal.py`, `aurum/rules/us/texas.py` — every rule's `compute()` takes `lang`.
- `aurum/rules/crossborder/rules.py` and `aurum/crossborder/assessment.py`'s `flags[]`.
- `aurum/taxus/service.py` (threads `lang` into every `registry.get(...).compute(...)` call).
- `aurum/holdings/trades.py`, `aurum/creditreport/store.py`.
- `aurum/plan/scenarios/*.py` (all six scenario modules thread `lang` and go through `t()`).
- `aurum/business/invoices.py`, `aurum/business/kpis.py`, `aurum/business/payroll.py`.
- `aurum/reports/packs.py` section titles/notes (a single language, resolved from the
  workspace/`?lang=` like every other summary).
- `aurum/insights/i18n.py` → thin re-export of `aurum/core/i18n.py`.

Left deliberately untouched (see "What is not localized" above): KPI labels in report packs, plan
scenario JSON-schema field labels, `unverified_constants` keys, and all citation text.

## Testing

`tests/core/test_i18n_sweep.py` builds both demo workspaces (`demo-mx`, default `language: es`; and
`demo-us`, switched to `en` via `PUT /api/workspaces/demo-us {"language": "en"}`), hits a representative
set of router endpoints from each module listed above, and walks the JSON response
collecting every `summary`/`Step.label`/`title`/`note` string (excluding citation fields and KPI
labels — see above) to assert no English stop-words (`" the "`, `" and "`, `" for "`, ...) leak into the
Spanish responses and no Spanish stop-words (`" el "`, `" la "`, `" para "`, ...) leak into the English
ones. A third test confirms `?lang=` overrides the workspace's own language.

Tests that assert specific English text (YAML rule-vector `explain_contains`/`steps_contain`,
`tests/rules_us/test_us_rules.py`, `tests/crossborder/test_crossborder_api.py`) pass `lang="en"`
explicitly (a `lang: en` key in every YAML vector case's `inputs`, or `?lang=en` on the request).
